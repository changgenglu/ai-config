# 工作流程驗證指南

> 供主代理在驗證期間參考。包含觀察指標定義、判定標準、驗證順序、歷史追蹤項目。

---

## 觀察指標（V1-V10）

| # | 指標 | 觀察方法 | 判定標準 |
|---|------|---------|---------|
| V1 | 審查無效標記率 | 🔵建議數 / 總發現數 | < 20%（改善前 40-60%） |
| V2 | 子代理歧義回報 | 遇到模糊規格時是否回報 BLOCKED/ESCALATE 而非硬猜 | 回報 > 0 次 = Escalation 生效 |
| V3 | 狀態行覆蓋率 | `.claude/reports/` 下報告是否都有 DONE/PARTIAL/BLOCKED/ESCALATE 狀態行 | 100% |
| V4 | 完成驗證遵循 | 子代理 DONE 時是否附上驗證指令的實際輸出（測試通過數、exit code） | 100% |
| V5 | Gemini 研究準確率 | 抽查 @gemini-researcher 「✅ 已驗證」的 2-3 項，用 Grep/Read 確認 | 100% 正確 |
| V6 | 平行派出效益 | @gemini-researcher 是否提供了主任務代理未涵蓋的互補資訊 | 有互補 = 值得；高度重疊 = 降頻 |
| V7 | 分析型替代方案 | @architect / @planner 報告是否含 3+ 替代方案 + tradeoff | 有 = Thinking Budget 生效 |
| V8 | XML vs 非 XML 遵循率 | 比較 XML 試點代理（3 個）與非 XML 代理的格式偏差、Escalation 觸發 | XML 更穩定 = 可擴展 |
| V9 | common-guardrails 有效性 | Edit 失敗時子代理是否在第 2 次即停止（而非繼續重試） | 第 2 次停止 = 護欄生效 |
| V10 | Token 效率趨勢 | 記錄任務 token 總量（`rtk gain`），與類似規模任務比較 | 持平或下降 + 品質提升 = 成功 |

### 指標詳細說明

**V1 審查無效標記率**：過度標記浪費使用者閱讀審查報告的時間。Few-Shot 反例 + Thinking Budget「沒問題就說沒問題」應直接影響此指標。

**V2 子代理歧義回報**：Escalation 結構化 + Thinking Budget「不推論，遇歧義回報」是 Phase 1+2 的核心改善。若子代理仍然硬猜，說明指令未生效。

**V5 Gemini 研究準確率**：整個 Gemini 輔助機制的信任基礎。若驗證不可靠，@gemini-researcher 反而是負擔。

**V6 平行派出效益**：@gemini-researcher 的核心價值是「平行偵察帶來互補資訊」。高度重疊 = 多花 token 無收益。

**V8 XML vs 非 XML**：決定是否將 XML 結構擴展到剩餘 13 個代理的關鍵數據。

**V9 common-guardrails 有效性**：引用式護欄的可靠性是假設，需實測。若無效需改為內嵌。

## 建議驗證順序

| 任務類型 | 重點驗證指標 | 目的 |
|---------|------------|------|
| 第 1 個（小型修復，路徑 C） | V2, V3, V9 | 最低成本驗證基本機制 |
| 第 2 個（中型功能，路徑 B Wave） | V1, V6, V7, V8, V10 | 完整流程 + Gemini 平行 + 審查品質 |
| 第 3 個（涉及安全/金流） | V5, V6 + 結果合併矛盾標註 | Gemini 驗證可靠性 + 合併規則 |
| 第 4-5 個 | 全部指標 + H1-H10 歷史項目 | 累積足夠資料做批次升級決策 |

## 批次升級決策

| 條件 | 行動 |
|------|------|
| 5/5 完成 + 品質 ≥ 70 + 無重大阻塞 | 產出優化報告 + 提議批次 2（brainstorming + writing-plans） |
| 5/5 完成 + 品質 < 70 | 產出問題分析 + 先修復批次 1 問題 |
| 任何時候發現重大流程問題 | 立即修復 + 記錄 + 回報使用者 |

## 重大問題即時處理規則

| 情況 | 行動 |
|------|------|
| 流程阻塞（兩套系統衝突、路徑找不到、狀態解讀錯誤） | 立即修復 + 記錄根因 + 回報使用者 |
| 整體品質 < 70 分 | 立即分析根因 + 提出優化方案 + 暫停後續驗證 |
| 子代理連續 2 個任務忽略方法論引用 | 強化該代理提示詞 + 記錄改善 |
