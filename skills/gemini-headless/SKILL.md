# Gemini Headless — 大量資料分析輔助技能

## 定位

利用 Gemini CLI 的無頭模式（`gemini -p`）與超長上下文窗口，**分擔大量資料的讀取與初步分析工作**，降低 Claude 子代理的 token 消耗並提高效率。

**Gemini 是偵察兵，不是工程師。** 他負責蒐集情報、提供觀點、初步分析——最終判斷與產出由 Claude 子代理把關。

---

## 適用場景（白名單）

| 場景 | 說明 | 範例 |
|------|------|------|
| **日誌分析** | 大量 log 的模式辨識、錯誤追蹤、時序分析 | 分析 500 行錯誤日誌找出根因 |
| **大範圍程式碼搜尋** | 跨模組的依賴追蹤、影響範圍掃描、呼叫鏈分析 | 搜尋所有使用某 Service 的檔案並整理呼叫關係 |
| **網路資料查詢** | 查閱技術文檔、API 文件、最佳實踐 | 查詢某框架的遷移指南 |
| **規劃批判性思考** | 對規劃方案提供不同角度的思考、挑戰假設 | 審視規劃報告的盲點與風險 |
| **審查多重驗證** | 作為額外審查視角，交叉比對發現 | 協助檢查 Controller 路由是否完整覆蓋 |
| **PDF / 大檔閱讀** | 利用長上下文讀取大型文件並萃取重點 | 讀取 50 頁技術規格文件 |
| **測試案例生成** | 生成測試案例草稿（仍需 Claude 審查修正） | 請 Gemini 用 qa-tester 技能產出測試骨架 |

## 禁止場景（黑名單）

| 禁止用途 | 原因 |
|----------|------|
| **撰寫實作程式碼** | Gemini 輸出品質不穩定，混入程式碼會導致反覆修正，token 成本反而更高 |
| **直接修改專案檔案** | 必須由 Claude 子代理執行所有寫入操作 |
| **作為最終產出** | Gemini 的任何輸出都只是「草稿」，必須經過驗證才能呈現給使用者 |
| **敏感資料處理** | 不傳入包含密碼、金鑰、個資的內容 |

## 指令模板

### 基礎指令

```bash
gemini -p "<PROMPT>" --approval-mode yolo -o text 2>/dev/null
```

| 參數 | 用途 |
|------|------|
| `-p "<PROMPT>"` | 無頭模式，傳入提示詞 |
| `--approval-mode yolo` | 自動允許工具呼叫（讀檔、搜尋等） |
| `-o text` | 純文字輸出，最乾淨 |
| `2>/dev/null` | 過濾 stderr 雜訊（MCP 載入、Keychain 等） |

### 唯讀模式（僅分析不動作）

```bash
gemini -p "<PROMPT>" --approval-mode plan -o text 2>/dev/null
```

### 指定工作目錄

```bash
cd /path/to/project && gemini -p "<PROMPT>" --approval-mode yolo -o text 2>/dev/null
```

### JSON 模式（需程式化解析時）

```bash
gemini -p "<PROMPT>" --approval-mode yolo -o json 2>/dev/null
```

回應在 `.response` 欄位，另含 `.stats` 提供 token 用量統計。

### 要求使用特定技能

Gemini 裝有與 Claude 相同的 skills，可在提示詞中指定：

```
請使用 pdf 技能讀取 /path/to/file.pdf 並萃取...
請使用 qa-tester 技能為以下模組設計測試案例...
請使用 critical-thinking 技能審查以下規劃方案...
```

## 提示詞撰寫規範（防幻覺）

Gemini 容易便宜行事、給出概數或編造不存在的內容。提示詞必須遵循以下原則：

### 1. 結構化 Checklist

永遠以明確的 checklist 格式下達任務，不給模糊指令：

```
❌ 「分析一下這個專案的狀況」
✅ 「請嚴格按照以下 checklist 逐項完成：
    - [ ] 項目 1：具體要求
    - [ ] 項目 2：具體要求
    每項必須附上佐證來源。」
```

### 2. 強制佐證

每項回答必須附上「佐證來源」（讀取的檔案路徑或執行的指令）：

```
每項回答必須包含「佐證來源」（你讀取的檔案路徑或執行的指令）。
如果某項無法取得資訊，明確寫「❌ 無法取得：原因」，禁止編造。
```

### 3. 禁止猜測聲明

在提示詞開頭加入角色約束：

```
你是一個嚴謹的調查員。禁止猜測、禁止使用「大約」「可能」等模糊用語。
只報告你實際讀取或執行後確認的事實。
```

### 4. 限定輸出格式

指定 Markdown 表格、列表或特定結構，避免散文式回答：

```
輸出格式：Markdown 表格，欄位為 | 檔案路徑 | 類別 | 說明 |
```

### 提示詞模板

```
你是一個嚴謹的{角色}。請嚴格按照以下 checklist 逐項完成，禁止猜測或省略。

## 調查 Checklist
- [ ] 項目 1
- [ ] 項目 2
- [ ] ...

## 輸出規則
1. 每項必須附上佐證來源（檔案路徑或指令）
2. 無法取得的項目寫「❌ 無法取得：原因」
3. 輸出格式：{指定格式}
4. 使用繁體中文回答
```

## 驗證協議（強制執行）

**Gemini 的任何輸出在呈現給使用者前，都必須經過以下驗證流程。**

### 驗證等級

| 等級 | 適用場景 | 驗證方式 |
|------|---------|---------|
| **L1 抽樣驗證** | 結構性資訊（檔案清單、目錄結構） | 抽樣 30% 項目用 Glob/Grep/Read 確認存在 |
| **L2 全量驗證** | 數值型資訊（數量、行數、端點數） | 用獨立指令重新計算，比對數值 |
| **L3 邏輯驗證** | 分析性結論（根因推斷、影響評估） | 讀取 Gemini 引用的原始資料，獨立判斷結論是否合理 |

### 驗證流程

```
1. 接收 Gemini 輸出
2. 依場景判斷驗證等級（L1/L2/L3）
3. 執行對應驗證
4. 標記驗證結果：
   - ✅ 已驗證正確
   - ⚠️ 部分偏差（附修正值）
   - ❌ 重大錯誤（丟棄該項，自行補充）
5. 整合驗證後的資料，產出最終結果
```

### 驗證報告格式（內部使用，不呈現給使用者）

```
## Gemini 輸出驗證
- 驗證等級：L{1/2/3}
- 抽樣/全量項目數：X
- 結果：✅ X 項 / ⚠️ X 項 / ❌ X 項
- 修正項目：{列出}
- 結論：{可信/需補充/不可用}
```

## 場景操作指南

### 場景 A：日誌分析除錯

```bash
# 將日誌內容透過 stdin 傳入
cat /path/to/error.log | gemini -p "
你是一個嚴謹的日誌分析師。分析以下日誌內容：

## Checklist
- [ ] 識別所有錯誤類型，列出錯誤訊息與出現次數
- [ ] 標記時間軸，找出錯誤首次與最後出現時間
- [ ] 分析錯誤間的因果關係（哪個錯誤觸發了後續錯誤）
- [ ] 提出可能的根因（必須基於日誌內容，不可猜測）

## 輸出格式
Markdown 表格 + 時序圖（文字版）
" --approval-mode plan -o text 2>/dev/null
```

驗證：L3 邏輯驗證 — 讀取日誌原文確認 Gemini 引用的行號與內容。

### 場景 B：大範圍程式碼搜尋

```bash
cd /path/to/project && gemini -p "
你是一個程式碼調查員。搜尋並分析以下目標：

## Checklist
- [ ] 找出所有使用 {ClassName} 的檔案，列出完整路徑
- [ ] 對每個使用點，列出呼叫方式與傳入的參數
- [ ] 繪製呼叫鏈（從 Controller 到最底層）

## 輸出規則
每項附上佐證（檔案路徑:行號），禁止編造。
" --approval-mode yolo -o text 2>/dev/null
```

驗證：L1 抽樣 — 隨機選 30% 檔案路徑用 Grep 確認。

### 場景 C：規劃批判性審查

```bash
cat /path/to/planning-report.md | gemini -p "
你是一個批判性分析師。請使用 critical-thinking 技能審查以下規劃報告。

## Checklist
- [ ] 識別規劃中的隱藏假設（哪些前提未被驗證？）
- [ ] 找出邏輯斷層（哪些步驟間缺乏推導？）
- [ ] 評估風險覆蓋（有哪些邊界情況未考慮？）
- [ ] 提出 2-3 個替代方案或優化建議

## 輸出規則
每項標記嚴重程度（🔴 高 / 🟡 中 / 🟢 低），附上引用段落。
" --approval-mode plan -o text 2>/dev/null
```

驗證：L3 邏輯驗證 — 逐項判斷 Gemini 的批評是否有理有據。

### 場景 D：審查多重驗證

```bash
cat /path/to/review-report.md | gemini -p "
你是一位獨立的程式碼審查員。以下是另一位審查員的報告，請進行交叉驗證。

## Checklist
- [ ] 逐項確認審查發現是否合理（讀取對應程式碼驗證）
- [ ] 找出原審查可能遺漏的問題
- [ ] 評估修復建議的可行性與副作用

## 輸出規則
對每項審查發現標記：✅ 同意 / ⚠️ 有疑慮 / ❌ 不同意，附理由。
" --approval-mode yolo -o text 2>/dev/null
```

驗證：L3 — 對 Gemini 不同意的項目，讀取原始碼獨立判斷。

## 效能與限制

| 項目 | 數值 |
|------|------|
| 單次呼叫耗時 | 10-60 秒（視任務複雜度） |
| 上下文窗口 | 極長（適合大量日誌/程式碼） |
| 準確率（結構性資訊） | ~90%+（需抽樣驗證） |
| 準確率（數值精確度） | ~80%（常有概數，需全量驗證） |
| 準確率（分析性結論） | ~70%（需邏輯驗證） |

## 成本效益

- Gemini 呼叫成本遠低於 Claude Opus/Sonnet
- 適合「廣度優先」的偵察任務，讓 Claude 專注「深度」的判斷與實作
- 一次 Gemini 偵察 + Claude 驗證 < Claude 獨自完成全部搜尋的 token 量

---

## 注意事項

1. **永遠不信任未驗證的 Gemini 輸出** — 他是助手，不是權威
2. **不用 Gemini 寫實作程式碼** — 品質不穩定，修正成本 > 自己寫
3. **不傳入敏感資料** — .env 內容、密碼、金鑰等
4. **超時處理** — 設定 Bash timeout（建議 120 秒），超時則放棄改用 Claude 直接處理
5. **錯誤回退** — Gemini 呼叫失敗時，子代理應自行完成任務，不阻塞流程
